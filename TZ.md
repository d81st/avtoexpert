## P0 — Авторизация (cookie-based)

### Контекст

JWT **остался**, но доставляется через HttpOnly cookies (`access_token`, `refresh_token`, `csrf_token`).  
Frontend хранит в `localStorage` только профиль (`auth-storage`), **не токен**.

Backend уже реализует: `POST /api/login`, `POST /api/logout`, `POST /api/refresh`, `GET /api/me`, CSRF middleware.  
Frontend **не вызывает** `/logout` и `/refresh` — только локальный `logout()` в zustand.

### Задача A1 — Аудит legacy-логики

**Цель:** убедиться, что старый JWT-flow нигде не мешает cookie-flow.

**Проверить (grep + ручной прогон):**

| Область | Что искать | Ожидание |
|---------|------------|----------|
| `frontend/src` | `Authorization`, `Bearer`, `localStorage` + `token`, поле `token` в store | **0** активного использования |
| `frontend/src/shared/api/client.ts` | `withCredentials: true` | ✅ есть |
| `frontend/src/features/auth` | ответ login содержит только профиль | ✅ без JWT в body |
| `backend/src` | чтение JWT из заголовка (кроме тестов) | только `req.cookies[access_token]` |
| Logout UI (`AppLayout`, `useAdmin`) | вызов `POST /api/logout` | ❌ сейчас нет |
| 401 interceptor | авто-refresh перед redirect | ❌ сейчас нет |

**Критерии приёмки:**
- [ ] Таблица аудита заполнена, найденные хвосты — в подзадачах A2/A3 или удалены.
- [ ] Login → работа 15+ мин → API не падает с 401 без попытки refresh.
- [ ] Logout → повторный `GET /api/me` → 401, cookies отсутствуют в DevTools.

### Задача A2 — Server logout

**Цель:** при «Выйти» сервер очищает все auth-cookies.

**Backend** (уже есть `POST /api/logout` → `authService.clearAuthCookies`):
- Без изменений, если endpoint работает.

**Frontend — изменить:**

| Файл | Действие |
|------|----------|
| `features/auth/api/authApi.ts` | `logout()` → `apiClient.post('/logout')` + `useAuthStore.logout()` |
| `app/routing/AppLayout.tsx` | `handleLogout` → await server logout |
| `features/admin/hooks/useAdmin.ts` | то же при выходе админа |

**Поведение:**
1. `POST /api/logout` (withCredentials)
2. При успехе или сетевой ошибке — всё равно `logout()` локально + `/login`
3. CSRF: `/logout` в exempt (`csrf.ts`) — заголовок не обязателен

**Критерии приёмки:**
- [ ] После выхода в Application → Cookies нет `access_token`, `refresh_token`, `csrf_token`.
- [ ] Повторный заход на `/` → редирект на `/login`.

### Задача A3 — Refresh на frontend

**Цель:** продлевать сессию по `refresh_token` (TTL 7 дней) без re-login каждые 15 мин.

**Backend** (уже есть `POST /api/refresh`):
- Читает `refresh_token` cookie (path `/api/refresh`)
- Выдаёт новую тройку cookies, body: `{ ok: true }`

**Frontend — добавить:**

| Компонент | Логика |
|-----------|--------|
| `features/auth/api/authApi.ts` | `refreshSession(): POST /refresh` |
| `shared/api/client.ts` | Response interceptor: при **401** (кроме `/login`, `/refresh`) → один раз `refreshSession()` → retry исходного запроса |
| Очередь | Параллельные 401 → один refresh, остальные ждут (mutex/flag) |
| Провал refresh | `logout()` + `window.location.href = '/login'` |

**Опционально:** proactive refresh за 1–2 мин до истечения access (низкий приоритет внутри A3).

**Критерии приёмки:**
- [ ] Access истёк, refresh валиден → запросы проходят без re-login.
- [ ] Refresh истёк → редирект на login, toast по желанию.
- [ ] `POST /login` с неверным паролем → **не** триггерит refresh.

## P1 — Фото в DOCX: замена 6 слотов шаблона

### Контекст / проблема

`original_example.docx` — предзаполненный отчёт с **6 встроенными статическими фото** (примеры в Word).

Задача 19.10 **добавила в конец** цикл `{#photos}…{/photos}` (`insert-photo-block.cjs`).  
Итог сейчас:
- 6 старых картинок остаются на своих местах;
- фото пользователя **дописываются в конец** циклом;
- размер новых — до 14 см по ширине (`MAX_IMAGE_WIDTH_EMU`), **не** размер оригинальных слотов.

### Целевое поведение

> Пользовательские фото **заменяют** 6 примеров в шаблоне **на тех же позициях** и **с теми же габаритами** (или пропорционально в рамках слота). Лишних фото в конце документа нет.

### Задача B1 — Переработка шаблона

**Вариант рекомендуемый:** 6 фиксированных слотов вместо append-loop.

| Шаг | Действие |
|-----|----------|
| 1 | В `original_example.docx` удалить статические изображения-примеры и append-блок `{#photos}` |
| 2 | На место каждого примера — плейсхолдер `{%photo_1}` … `{%photo_6}` (+ опционально `{caption_1}` … `{caption_6}`) |
| 3 | Зафиксировать **EMU-размеры** каждого слота из оригинала (скрипт инвентаризации / `word/document.xml`) |
| 4 | Обновить `templates/README.md` и `placeholderInventory.test.ts` |

**Альтернатива:** один цикл `{#photos}` **внутри** секции, где стояли 6 фото (без дубля в конце) — если слоты одинакового размера.

### Задача B2 — Генератор (`docGenerator.ts`)

| Изменение | Детали |
|-----------|--------|
| Scope | `photo_1..photo_6` (путь к файлу или `null`) вместо/вместе с массивом `photos[]` |
| `getSize` | Per-slot размеры из констант шаблона, не глобальные 14 см |
| `buildPhotoScope` | Маппинг `position` 1..6 → `photo_N`; слоты без файла → пусто/заглушка |
| Лимит | UI уже ≤20 фото; в DOCX — **макс. 6** в слотах (остальные — только UI или отдельное решение) |

### Задача B3 — Продуктовое решение по лимиту

Зафиксировать одно:
- **(a)** В DOCX только первые 6 по `position`;
- **(b)** Уменьшить лимит загрузки до 6;
- **(c)** Вторая страница для фото >6 (отдельная задача).

**Критерии приёмки:**
- [ ] Сгенерированный DOCX: 6 слотов = пользовательские фото, примеры не видны.
- [ ] Размер каждого фото соответствует слоту шаблона (визуальная проверка + unit на `getSize`).
- [ ] 0 загруженных фото → пустые слоты, без мусора в конце.
- [ ] 3 фото → заполнены слоты 1–3, 4–6 пусты.

## P2 — Хранилище: фото остаются, DOCX пересоздаётся

### Решение (зафиксировано)

> **PostgreSQL + фото на диске = всё для пересборки документа. Готовый `.docx` на сервере не храним.**

**Почему фото не удаляем:** пользователь может захотеть **пересоздать** тот же отчёт позже. Текстовые данные есть в БД, но без файлов в `uploads/photos/` картинки в DOCX восстановить нельзя — получится «нестыковка» (пустые места вместо фото). Поэтому фото **остаются локально** в `uploads/photos/` на весь жизненный цикл отчёта.

**Почему DOCX не храним:** это производный артефакт. Его можно собрать заново из:
- полей отчёта и связанных таблиц (БД);
- фото по `photos.file_path` (диск);
- шаблона `templates/original_example.docx`.

| Данные | Где | Политика |
|--------|-----|----------|
| Поля отчёта, работы, запчасти | PostgreSQL | хранить |
| Метаданные + `file_path` фото | PostgreSQL | хранить |
| Бинарники фото | `uploads/photos/` | **хранить** (локально, как сейчас) |
| Готовый `.docx` | `uploads/report_*.docx` | **не хранить** / удалять после отдачи |
| Шаблон | `templates/` | хранить (системный) |

### Задача C1 — Генерация без долгоживущего файла

Текущий flow (`finalize-and-generate` → `writeFile` в `uploads/`) изменить:

| Вариант | Описание |
|---------|----------|
| **A (предпочтительно)** | После `docGenerator.generateDocument()` — stream buffer в ответ или отдать при `GET /download` без записи на диск |
| **B** | Писать временно → удалить сразу после успешного `GET /download` |

`status = completed` в БД остаётся маркером «отчёт можно скачать/пересобрать», а не «файл лежит на диске».

### Задача C2 — Повторное скачивание = регенерация

`GET /api/reports/:id/download` для `completed`:
1. Читать данные из БД + фото с диска
2. Запускать `DocGenerator` (тот же pipeline, что при финализации)
3. Отдавать buffer клиенту
4. Не оставлять `report_*.docx` в `uploads/`

**Критерии приёмки:**
- [ ] После генерации/скачивания в `uploads/` нет `report_*.docx`.
- [ ] Повторный download отдаёт актуальный документ (с теми же фото).
- [ ] Фото в `uploads/photos/` сохраняются после `completed`.
- [ ] Удаление отчёта (`deleteReport`) по-прежнему чистит связанные фото с диска.

### Задача C3 — Опционально позже

- Cron: удаление **осиротевших** файлов (есть на диске, нет строки в БД)
- Лимит диска / ротация — только если понадобится на проде
